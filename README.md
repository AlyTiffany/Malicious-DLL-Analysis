# Malicious DLL Analysis

## Overview

This project documents my analysis of a malicious Windows DLL using a combination of **static and dynamic malware analysis techniques**.

The goal of the analysis was to examine the DLL's characteristics, observe its behaviour during execution, and identify useful **Indicators of Compromise (IOCs)**.

The analysis included:

- Examining the DLL's PE structure and metadata
- Identifying the compiler used to build the sample
- Reviewing exported functions
- Monitoring registry and filesystem changes
- Monitoring runtime process activity
- Checking common persistence locations
- Analysing network communication
- Identifying remote IP addresses and listening ports

---

## Tools Used

| Tool | Purpose |
|---|---|
| **Detect It Easy (DIE)** | Identify the file format and compiler |
| **PEStudio** | Examine PE metadata and compile information |
| **Hex Viewer** | Inspect the DLL's PE header |
| **Regshot** | Compare registry and filesystem state before and after execution |
| **Process Monitor** | Monitor registry, file, and process activity during execution |
| **Autoruns** | Review common Windows persistence mechanisms |
| **Wireshark** | Analyse network communication generated by the DLL |

# Static Analysis

## Compiler Identification

I began by examining the DLL using **Detect It Easy**.

The sample was identified as being compiled using:

**Embarcadero Delphi 10.2 Tokyo**

The linker was identified as:

**Turbo Linker 2.25**

![Detect It Easy compiler identification](images/dll_dynamic_compiler.png)

Identifying the compiler provides useful context about how the executable was constructed and can help guide further analysis.

---

## Compilation Timestamp

I examined the PE metadata using **PEStudio**.

The compiler timestamp was:

```text
2024-02-01 11:38:51 UTC
```

![PEStudio compilation timestamp](images/DLL_Dynamic_PEstudio_compile_date.png)

PE compilation timestamps can be modified or falsified, so the timestamp should not automatically be treated as proof of when the malware was created. However, it remains useful metadata when combined with other findings.

---

## PE Header

I also inspected the DLL at the hexadecimal level.

The first two bytes of the file were:

```text
4D 5A
```

![DLL hexadecimal header](images/pe-header-hex.png)

`4D 5A` represents the **MZ signature**, which is expected at the beginning of a Windows Portable Executable (PE) file.

The DLL was also found to contain:

```text
4 exported functions
```

Exported functions are particularly relevant when analysing DLLs because they can indicate how the library is intended to be called or executed.

# Dynamic Analysis

After completing the initial static analysis, I executed the DLL in an isolated lab environment and monitored its behaviour.

The DLL was executed using **rundll32.exe**.

---

## Regshot Baseline

Before executing the DLL, I used **Regshot** to capture a baseline snapshot of the system.

![Regshot baseline](images/regshot-baseline.png)

After execution, I captured a second snapshot and compared the system state.

![Regshot comparison](images/regshot-comparison.png)

The comparison reported:

| Change | Count |
|---|---:|
| Keys deleted | 20,300 |
| Keys added | 31 |
| Values deleted | 23,912 |
| Values added | 95 |
| Values modified | 129 |
| Folders deleted | 0 |
| Folders added | 0 |
| Files deleted | 0 |
| Files added | 0 |
| Files/attributes modified | 3 |
| **Total changes** | **44,467** |

The large number of changes does **not** mean that all 44,467 changes were caused by the DLL.

Windows and other running applications continuously generate registry and filesystem activity. Regshot therefore provided a useful comparison point, but additional tools were needed to determine which activity was actually associated with execution of the sample.

---

## Process Monitor

I used **Process Monitor (ProcMon)** to get a more detailed view of activity occurring while the DLL executed.

![Process Monitor DLL activity](images/procmon-rundll32.png)

Filtering the capture around `rundll32.exe` allowed me to examine operations associated with the process executing the DLL.

Observed activity included operations such as:

```text
RegOpenKey
RegQueryKey
RegQueryValue
RegSetValue
QueryNameInformationFile
CloseFile
```

This provided greater visibility into the registry and filesystem activity occurring during execution than the Regshot comparison alone.

Using both tools was useful because **Regshot provided a before-and-after comparison**, while **ProcMon provided individual runtime events** that could be investigated more closely.

# Persistence Analysis

## Autoruns

I also used **Sysinternals Autoruns** to review common Windows autostart and persistence locations.

![Autoruns persistence review](images/autoruns-comparison.png)

This included examining areas such as:

- Scheduled Tasks
- Services
- Logon entries
- Drivers
- Winlogon
- WMI
- Known DLLs

The screenshot shows scheduled tasks including Microsoft Edge update tasks and `npcapwatchdog`.

Their presence alone does not establish that they were created by the malicious DLL. Autoruns was used as another source of evidence to identify suspicious persistence mechanisms that could then be correlated with the other analysis results.

# Network Analysis

I used **Wireshark** to examine network communication attempts generated while the DLL was executing.

The analysis identified communication associated with the following remote IP addresses:


These network observations provided some of the most useful Indicators of Compromise identified during the analysis.

# Key Findings

The analysis identified several important characteristics of the DLL.

The sample was compiled using **Embarcadero Delphi 10.2 Tokyo** and contained **four exported functions**.

Static analysis provided information about the DLL's structure and metadata, while dynamic analysis allowed me to observe how the sample interacted with the system after execution.

The most significant behavioural findings were the DLL's network activity involving:

```text
109.234.38.247
46.149.77.41
```

and the creation of a listener on:

```text
TCP 31614
```

These provide useful network indicators that could be used during further investigation or threat hunting.

---

# What I Learned

This lab demonstrated why malware analysis benefits from using multiple tools rather than relying on a single source of evidence.

**Static analysis** quickly revealed information about the DLL without requiring execution, including its compiler, timestamp, PE structure, and exports.

**Dynamic analysis** revealed behaviour that became visible only after the DLL was executed, including registry activity, filesystem activity, and network communication.

The Regshot results also demonstrated the importance of distinguishing **correlation from attribution**. A large number of system changes occurred between snapshots, but that does not mean every change was caused by the malware.

Tools such as ProcMon, Autoruns, and Wireshark helped provide additional context and allowed individual behaviours to be investigated rather than assuming that every observed system change was malicious.

Overall, the exercise strengthened my understanding of how static analysis, host-based monitoring, and network analysis can be combined to develop a more complete picture of a suspicious file's behaviour.
